TITLE

A Fallback-Aware Hybrid System for AI-Assisted Travel Planning: Integrating Point-of-Interest Recommendation, Itinerary Generation, and Geospatial Optimization


ABSTRACT

Travel planning involves selecting points of interest (POIs), arranging visits into a feasible itinerary, and accounting for geographic and practical constraints. This paper describes the design and implementation of an AI-assisted travel-management system that combines structured travel data with language-model generation and geographic planning. The system retrieves POI candidates from its database and ranks them using preference match, candidate quality, proximity, and data completeness through scorePoi(). Gemini is used to generate itinerary content, which is validated before use; when itinerary generation fails validation, the system can construct a deterministic itinerary. Geographic services support geocoding and routing, with alternatives including LocationIQ and static city coordinates for geocoding, and Haversine-based distance estimates when road routing is unavailable. The application also integrates trip budgeting and expenses, image enrichment, and a Cesium-based 3D POI view.

The paper focuses on this hybrid architecture and its implemented fallback paths, including the capabilities and limitations of those fallbacks. It does not assume that the system consistently recommends a destination's most important attractions or that its fallbacks preserve the same accuracy as primary services. Recommendation relevance and resilience under simulated service failures require quantitative evaluation before performance claims can be made.


KEYWORDS

Travel planning system; personalized itinerary generation; point-of-interest recommendation; geospatial planning; multi-criteria ranking; fallback handling; full-stack web application.


1. INTRODUCTION

Travel planning requires decisions about which places to visit, where to stay, where to eat, how to travel between locations, and how to fit these activities into a schedule and budget. These decisions are interdependent: selecting attractions without considering their locations, opening hours, visit durations, or the traveler's available time can produce an itinerary that is difficult to follow. A travel-planning system must therefore do more than return a list of popular places; it must organize candidate destinations and practical constraints into a usable trip plan.

This paper presents Travel Manager, a web application for creating and managing trips. Users provide trip details, including destination, dates, budget, and travel preferences. The system retrieves candidate points of interest (POIs), hotels, and restaurants from its travel data, ranks candidates, and uses Gemini to generate structured trip content. The itinerary generation pipeline validates the model's output and applies scheduling and geographic processing. The application also provides map-based trip views, budget and expense tracking, and trip-management features.

The system combines AI generation with conventional application logic. For example, scorePoi() ranks POI candidates using preference match, candidate quality, proximity, and data completeness. Gemini-generated itinerary data is checked by validateItinerary() before being used. When valid AI itinerary output is unavailable, the generation pipeline can use buildDeterministicItinerary(). For geographic planning, the system uses Geoapify and LocationIQ services where available, with a static city-coordinate lookup for supported destinations; route timing can fall back to an estimate based on Haversine distance. These alternatives allow some planning functions to continue when a provider is unavailable, although fallback estimates do not provide the same detail or accuracy as live road-routing data.

The study focuses on the design of this hybrid planning pipeline and the fallback behavior implemented around its external dependencies. It does not assume that the system always identifies a destination's most important attractions, produces an optimal route, or maintains equivalent accuracy when a primary service fails. Recommendation quality, itinerary feasibility, and fallback effectiveness require evaluation against defined test cases and comparison methods.


1.1 PROBLEM DEFINITION AND OBJECTIVES

The problem addressed is the generation of a structured travel plan from user-provided trip constraints and available destination data. The system must retrieve travel candidates, account for user preferences and geographic context, and produce an itinerary whose activities are associated with trip days and scheduling information. It must also handle cases in which candidate data is incomplete or an external service does not return a usable result.

The objectives of this work are to:

1. Describe a travel-planning workflow that combines database-based candidate retrieval, multi-criteria POI ranking, AI-generated itinerary content, and geographic scheduling.
2. Document the validation and deterministic alternatives used when AI-generated itinerary data cannot be accepted.
3. Examine how the system degrades when geographic or enrichment services are unavailable.
4. Identify evaluation methods for assessing recommendation relevance, itinerary feasibility, and fallback behavior.


1.2 RESEARCH QUESTIONS

RQ1: How does the system combine destination data and user preferences to rank travel candidates for an itinerary?

RQ2: To what extent do the generated itineraries satisfy defined scheduling and geographic constraints?

RQ3: Which planning functions remain available when AI, geocoding, or routing services fail, and what information or accuracy is lost?

These are evaluation questions, not reported findings. The paper should answer them using measured results; where such evaluation has not been conducted, the results should be presented as future work rather than inferred from the implementation.


1.3 PAPER ORGANIZATION

It then presents implementation details, fallback mechanisms, and the evaluation methodology and results. The final sections discuss the contribution and limitations of the system and identify future work.

REVISION NOTES FOR THE CURRENT DRAFT

1. Project name and title
   The supplied paper title uses "TripWeaver", while the body uses "Travel Manager". Choose one project name and apply it consistently. The title also says "Real Time Dynamic"; the current draft does not establish real-time itinerary adaptation or live availability. Remove those terms unless those behaviors are demonstrated and evaluated.

2. Unrelated material in Related Work
   The current draft includes material about AgentForge AI, software-development lifecycle agents, LangGraph, ChromaDB, FastAPI, and related topics. This material describes a different project and should be removed. Replace it with research relevant to travel recommendation, itinerary planning, geospatial optimization, AI-assisted trip planning, and fallback-aware systems.

3. POI scoring weights and AHP statement
   The current implementation of scorePoi() in server/src/services/recommendation/poiRecommendation.service.js uses:
   WEIGHTS = { preference: 0.25, quality: 0.55, proximity: 0.1, dataQuality: 0.1 }
   The existing draft reports different POI weights (0.50, 0.35, 0.15) and says the weights were selected with the Analytic Hierarchy Process. The code inspected does not establish that AHP was used. Correct the weights and remove the AHP claim unless there is independent methodological documentation. Verify hotel and restaurant scoring separately before retaining any weights for those item types.

4. Candidate caps
   The existing draft reports fixed limits of 60 POIs, 25 hotels, and 40 restaurants. In the current server/src/services/recommendation/candidate.service.js, the corresponding candidate-cap constants are null. POI recommendations are subsequently limited by the target count and TOP_N_FOR_GEMINI in poiRecommendation.service.js. Do not state the old database candidate caps as current behavior unless another active configuration verifies them.

5. Geographic clustering
   The implementation uses clusterPOIsByDay() in server/src/services/itinerary/clustering.service.js. It is described in code as a simple k-means-style approach with deterministic centroid initialization, rebalance logic, and round-robin distribution for POIs without coordinates. Describe those details rather than claiming an unqualified or optimal k-means solution.

6. Haversine route fallback
   The route fallback uses Haversine straight-line distance and an estimated duration. It is not a road-distance calculation. Revise any wording that describes the fallback value as actual driving distance or actual driving time. State that it is an estimate and that it lacks road geometry.

7. Results versus proposed evaluation
   The current Results and Screenshots section shows interface screens. Section 6.1 describes evaluation that would be useful, but it does not report that those tests were conducted. Relabel or reorganize that material as Evaluation Methodology/Planned Evaluation until measurements exist. Do not treat screenshots or unit-test results as evidence of recommendation effectiveness.

8. Novelty and effectiveness claims
   The draft's claim that the system demonstrates an "effective" approach or that its method is novel requires comparative evidence. Present the integration of ranked structured candidates, validated AI generation, geographic scheduling, and implemented fallbacks as the system's design/contribution candidate. Establish novelty through related-work comparison and evaluation rather than assertion.

9. Literature references
   The current reference list contains duplicate numbering and references associated with the unrelated AgentForge AI material. Remove irrelevant entries, repair numbering, verify publication details, and ensure each retained reference supports a cited statement in the travel-planning paper.

10. Implementation accuracy
    Recheck descriptions of live transport data, weather handling, image lookup, public/private data, and 3D behavior against the code before retaining broad claims. Distinguish real provider results from generated estimates, cached data, deterministic defaults, and unavailable features.
